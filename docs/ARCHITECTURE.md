# Архитектура ZakonExpert

## Границы рефакторинга

Сайт остаётся приложением Node.js 22.5+ / Express / EJS с существующими
SQLite-адаптерами и статическими страницами. Новый фреймворк, сборщик,
зависимости или миграция базы данных не требуются. Рефакторинг разделяет
ответственность кода, не меняя дизайн, публичные URL и контракты API.

## Ответственность модулей

| Путь | Ответственность |
| --- | --- |
| `server.js` | Загружает `.env` и запускает сервер; точка входа `npm start` и Passenger |
| `app/start.js` | Собирает рабочее окружение, запускает фоновые задания и HTTP-сервер |
| `app/config.js`, `app/runtime.js` | Читают конфигурацию и связывают логирование с источниками данных |
| `app/services.js` | Подключает существующие адаптеры SQLite, КГД, Госзакупа, Telegram и импортеры |
| `app/create-app.js` | Создаёт Express-приложение и регистрирует обработчики; не слушает порт и не запускает задания |
| `app/http/` | Защитные заголовки, перенаправления, раздача файлов, авторизация, лимиты запросов и обработка ошибок |
| `app/routes/` | Маршруты 15 групп: реестры, каталоги, услуги, проверки, законы, новости, sitemap, поиск, открытые данные, инструменты, обращения и администрирование |
| `app/catalog-data.js` | Чтение CSV-каталогов, нормализация, локальные кэши и применение существующих privacy-исключений |
| `app/news-format.js` | Форматирование заголовков, RSS/XML и SVG-обложек новостей |
| `app/background-jobs.js` | Существующие импорты, расписания обновлений и очистка данных по срокам хранения |
| `app/paths.js` | Единый корень проекта для файлов независимо от текущего рабочего каталога |
| `modules/` | Предметная логика, адаптеры данных, поиск, SEO и правила приватности |
| `views/`, `views/partials/` | EJS-страницы и переиспользуемые фрагменты |
| `public/` | Статические страницы, стили, изображения и клиентский JavaScript |

`createApp({ config, services, logger })` получает зависимости явно. В тестах
вместо реальных баз и внешних сервисов передаются небольшие адаптеры.
Лимиты HTTP-запросов и кэши CSV создаются для каждого экземпляра приложения.
Конструирование HTTP-приложения не запускает cron, Telegram polling,
импорты или очистку баз. Рабочие адаптеры при этом сохраняют прежнюю модель
подключения и не предназначены для нескольких независимых production-сайтов
в одном процессе.

`startServer()` остаётся производственной точкой запуска. Как и раньше,
`DISABLE_BACKGROUND_JOBS` отключает периодические задания и Telegram polling,
но не обязательный локальный импорт нотариусов/ЧСИ и очистку данных по срокам
хранения. Массовый прогрев открытых данных на Passenger по-прежнему следует
запускать отдельной задачей Plesk; см. `docs/PLESK-STORAGE.md`.

## Порядок HTTP-обработки

1. Настройка Express/EJS, CSP и других защитных заголовков.
2. Compression, CORS и разбор JSON.
3. Канонические перенаправления и запрет доступа к `/data` — до статических файлов.
4. Раздача `public/`, учёт посещений и тайм-ауты.
5. Маршруты разделов. Внутри раздела более точные пути должны предшествовать
   параметризованным и общим обработчикам.
6. Реальные 404 и обезличенный обработчик ошибок — строго последними.

Проверка списка маршрутов фиксирует методы и пути, но не доказывает правильность
их порядка. Поэтому обязательны также HTTP-проверки конкретных адресов,
редиректов и ошибочных запросов.

## Общая клиентская логика

`public/js/site.js` инициализируется один раз даже при повторном подключении
скрипта. Общие контролы запускаются и до, и после `DOMContentLoaded`:

- `initializeGlobalSearch` — единая строка поиска;
- `initializeNavigation` — мобильное меню и общие пункты;
- `initializeFooter` — год и юридическая подпись;
- `initializeWhatsApp` — контактный QR-блок только на разрешённых страницах;
- `initializeContactForm` — согласие, отправка обращения и переход в WhatsApp.

Маркер `data-suppress-zakonexpert-contacts` на корневом HTML-элементе карточки
организации обязателен. Нельзя добавлять туда телефоны ZakonExpert, плавающие
контакты, WhatsApp или призывы обратиться в юридический сервис. На остальных
страницах сохраняется прежнее поведение.

Общие HTML-фрагменты должны быть EJS-partial с экранированным `<%=` для данных.
Для необходимой серверной конкатенации HTML используйте `escapeHtml` из
`modules/html.js`; это экранирование текста и атрибутов, а не проверка URL.
Результат поиска, названия организаций и импортированные строки нельзя
вставлять как доверенный HTML. Пример — `views/partials/bank-arrest-guide.ejs`.

## Как добавить или изменить маршрут

1. Выберите соответствующий файл `app/routes/`. Новый домен регистрируйте
   явно в `app/create-app.js` перед обработчиками ошибок.
2. Передавайте рабочие сервисы через `dependencies`, не открывайте базы и не
   запускайте фоновые задания внутри HTTP-регистрации.
3. Для асинхронного обработчика используйте `asyncHandler`; для служебных
   действий — существующую авторизацию и соответствующий rate limiter.
4. Сохраните канонические URL, реальные 404/410, правила индексации и
   privacy-исключения. Они применяются не только к HTML, но и к API,
   поиску, JSON-LD и sitemap.
5. Добавьте HTTP-тест и предметный тест. При намеренном изменении публичного
   контракта обновите `scripts/fixtures/http-routes.json` вместе с пояснением.
   Не перегенерируйте fixture только ради устранения регрессии.

## Проверки

```bash
npm run test:architecture
npm run test:site-shell
npm test
```

На момент разделения серверного кода fixture содержит 222 регистрации
методов/путей исходного сервера. Архитектурный тест сравнивает их с новым
приложением и выполняет 178 HTTP-проверок: публичные страницы, детали каталогов,
локали, поиск, приватность, редиректы, служебные методы, обработка ошибок и
кэш проверки компании. Используются синтетические данные и заглушки внешних
сервисов; тест не отправляет сообщения и не обращается к государственным API.

Тест общей оболочки проверяет восемь сочетаний готовности DOM, языка и
запрета контактов, а также отсутствие дублирующихся элементов и обработчиков.
Он не заменяет визуальную проверку в браузере.

Полный `npm test` дополнительно запускает существующие проверки реестров,
импорта, SEO, приватности, HTML, CSS и smoke-тест производственной точки входа.
`scripts/check-js.js` автоматически проверяет JavaScript в `app/`, `modules/`,
`public/js/` и `scripts/`, не обходя зависимости, скрытые каталоги и симлинки.

## Выпуск и откат

1. Запустите полный `npm test`, проверьте diff и отсутствие ключей, выгрузок,
   SQLite-файлов и пользовательских материалов в коммите.
2. Обновите `modules/release-config.js`. `/health` и проверка выпуска
   используют один идентификатор версии.
3. Опубликуйте ветку и PR в `main`, дождитесь успешных CI-проверок.
4. Перенесите `main` отдельным PR в `migration/zakonexpert-kz`, сохраняя
   дополнительные изменения ветки размещения.
5. В Plesk: «Получить сейчас» → «Развернуть сейчас»; при необходимости
   перезапустите Node.js-приложение. Убедитесь, что развёрнут весь каталог
   `app/`, а не только новый короткий `server.js`.
6. Проверьте идентификатор `/health`, основные страницы и privacy-исключения
   на живом домене. Успешный merge в GitHub сам по себе не подтверждает,
   что Passenger уже обслуживает новый код.

Для отката используйте отдельный revert-коммит через обычный PR и повторный
деплой. Рефакторинг не меняет схему или содержимое рабочих баз: откатывать или
восстанавливать SQLite ради него не нужно. Не используйте откат всего сайта к
старой версии, если это отменяет уже выпущенное удаление персональных данных.
