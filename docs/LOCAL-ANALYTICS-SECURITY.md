# Безопасность локальной аналитики (backend)

Проверены: `modules/clicks-db.js`, `server.js` (`/api/track-click`, `/api/track-event`), `data/clicks.db`.

## Проверено и подтверждено безопасным

| Пункт | Статус |
|---|---|
| Нет публичного эндпоинта, читающего `clicks.db` целиком | ✅ `getStats()` существует в `clicks-db.js`, но нигде не подключён ни к одному HTTP-маршруту — прочитать базу через сайт нельзя вообще, ни авторизованно, ни нет |
| Нет эндпоинта, позволяющего удалить данные аналитики | ✅ В `clicks-db.js` нет функции удаления, соответственно и в `server.js` такого маршрута нет |
| Нет произвольных запросов к базе через параметры клиента | ✅ Клиентские данные используются только как **значения** при `insert()`, никогда как ключи `find()`/`update()` — NoSQL-инъекция через операторы (`$where` и т.п.) неприменима к используемому паттерну |
| ИИН/телефон/email/текст сообщения/содержимое документа не сохраняются | ✅ Ни один вызов `recordClick()` из `server.js` не передаёт эти поля |
| `/api/track-event` — имена событий ограничены белым списком | ✅ `ANALYTICS_EVENT_TYPES` (`server.js`) — неизвестный `type` отклоняется (`{ok:false}`) |

## Найдено и исправлено в этой сессии

1. **`/api/track-click` не имел белого списка `type`/`target`.** Любая строка принималась и: (а) записывалась в `clicks.db`, (б) **пересылалась в Telegram владельцу** через `telegram.notifyClick()`. Это открывало вектор для спама произвольными сообщениями в Telegram-уведомления путём прямых POST-запросов к эндпоинту, в обход UI сайта. Исправлено: добавлены `TRACK_CLICK_TYPES = {'phone','whatsapp'}` и `TRACK_CLICK_TARGETS = {'main','advocate','mediator'}` — точно те значения, которые реально отправляет `chatbot.js`. Любое другое значение теперь отклоняется до записи в базу и до отправки в Telegram.
2. **Отсутствовал предел длины полей.** Клиент мог отправить сколь угодно длинную строку в `target`/`page`/`ua`, засоряя базу и уведомления. Добавлено ограничение 300 символов на строковое поле в `clicks-db.js` (функция `clip()`), применяется ко всем записям обоих эндпоинтов одинаково.
3. **База не создавала родительскую директорию `data/`, если её нет.** `NeDB` не создаёт директорию сама — если бы `data/` отсутствовала на новом окружении (например, при разворачивании из архива без сохранения пустых папок), первая запись в `clicks.db` привела бы к падению. Добавлено `fs.mkdirSync(DATA_DIR, { recursive: true })` перед созданием `Datastore` — теперь директория создаётся автоматически, если её нет.

## Найдено, не изменялось (вне рамок аналитики)

`/admin/comments` использует пароль в query-строке (`?pw=`), сверяемый с `process.env.ADMIN_PW`. Найдено и исправлено в этой сессии: в коде был захардкожен дефолтный пароль, использовавшийся, если переменная окружения не задана — это значение уже лежало в открытом виде в git-истории репозитория и должно считаться скомпрометированным. Убрано: теперь при отсутствии `ADMIN_PW` в окружении админ-маршруты возвращают 403 для любого пароля (нет рабочего дефолта). **Требуется ручное действие:** убедиться, что на сервере в `.env` задан `ADMIN_PW` со своим сложным значением — иначе `/admin/comments` станет недоступен после деплоя.

Отдельно, вне рамок этого исправления: передача пароля через query-строку означает, что он может попасть в логи сервера/прокси и заголовок Referer — сам механизм авторизации стоит в будущем заменить на более надёжный (например, HTTP Basic Auth или сессионный логин). Это не относится к аналитике кликов, но обнаружено в ходе аудита рядом с ней.

## Обработка ошибок записи

Все вызовы `recordClick()` в `server.js` оборачены в `.catch(() => {})` — ошибка записи в базу никогда не приводит к падению запроса или необработанному исключению; она просто теряется молча (осознанный компромисс: аналитика не должна быть настолько важной, чтобы блокировать ответ пользователю).
