# Аудит дизайна и UX — ZakonExpert (Этап 14.1)

Аудит выполнен без изменения кода, по факту (grep, чтение файлов, подсчёт). Задача — понять реальное состояние перед любым редизайном, не гадать.

## 1. Какие стили используются сейчас

| Файл | Размер | Назначение |
|---|---|---|
| `public/css/landing.css` | 64K | Главная дизайн-система: `@font-face` (Manrope), свой `:root` (`--sky-*`, `--gold-*`, `--ink-*`), header/nav/hero/кнопки/footer. Подключён на всех 42 страницах. |
| `public/css/style.css` | 28K | Второй слой — форма проверки, поиск, спиннер загрузки. На 41 странице. |
| `public/css/news.css` | 24K | Стили новостного хаба/статьи. **Свой хардкод цветов, без `:root`.** Через `views/news/layout.ejs` фактически подключён на всех EJS-страницах (карточки ЧСИ/нотариусов, каталоги, статьи законов) — не только на новостях. |
| `public/css/legal.css` | 16K | Стили `/zakony` и денежных страниц. **Свой отдельный `:root` (`--legal-*`)**, не связан с `landing.css`. |
| `public/css/styles.css` | 4.6K | Легаси — стили результатов поиска. **Ни разу не подключён ни в одном `<link>`** — похоже на мёртвый CSS, кандидат на удаление (требует подтверждения перед удалением). |

**Архитектурная особенность:** все EJS-страницы (карточки ЧСИ/нотариусов, каталоги банков/МФО/ломбардов и т.д.) не имеют своего `<head>`/`<html>` — тело собирается JS-строкой и передаётся в `views/news/layout.ejs`, который и есть общий header/footer. Статические `public/*.html`-страницы **дублируют** тот же header/footer вручную в каждом файле (проверено: `index.html` и `layout.ejs` почти идентичны в этом блоке). Значит любое изменение шапки/подвала нужно вносить в ~42 файла отдельно — сам по себе источник рассинхронизации.

## 2. Где стили дублируются

**Три параллельные цветовые системы**, не связанные друг с другом:
- `landing.css` → `--sky-950:#0e2a47` … `--sky-700:#1f6cae`, `--gold-500:#d7a742`
- `legal.css` → `--legal-dark:#0b1f35`, `--legal-blue:#1a4a7a`, `--legal-gold:#d4a83a` — другой тёмно-синий и другое золото
- `news.css` → без `:root` вообще, хардкод `#0f2044`/`#1a3560` — третий оттенок навy

Плюс инлайн-стили в отдельных страницах добавляют ещё цвета: `#f0c040`, `#ffd55a` (index.html, dokumenty.html — четвёртый вариант золота), `#1a56db` (views/bailiff/page.ejs:77 — отдельный синий для одной кнопки).

**Кнопки:** ~13 разных `.btn-*` классов, многие — почти дубли друг друга. Например `.btn-landing` (landing.css) и `.btn-legal-cta` (legal.css) — оба «золотой градиент CTA», но с разными переменными, паддингами и радиусами.

**Карточки:** ~30 разных card-классов (`.service-card`, `.cc-card`, `.process-card`, `.feature-card`, `.value-card`, `.problem-card`, `.step-card`, `.pro-card` и т.д.) — большинство визуально решают одну и ту же задачу «иконка + заголовок + текст», но реализованы независимо.

## 3. Какие страницы визуально отличаются без причины

Денежные страницы (`legal.css`) и карточки ЧСИ/нотариусов/каталоги (`news.css`) используют разные оттенки того же «фирменного» синего и золотого — из-за трёх несвязанных цветовых систем (см. п.2), а не из-за осознанного дизайн-решения.

## 4. Где слабый контраст

Не выявлено явных случаев текста на фоне того же тона (WCAG-нарушений не найдено в выборке), но 5 разных «зелёных» (`#25d366`, `#22c55e`, `#2e7d32`, `#15803d`, `#4ade80`) для одной и той же семантики «успех/WhatsApp» создают визуальную неоднородность, которая может выглядеть как ошибка, а не стиль.

## 5. Где текст сливается с фоном

Не обнаружено критичных случаев в выборке. Требует точечной проверки при переходе к конкретным страницам (не проверялось экранно/скриншотами на этом этапе).

## 6. Где слишком маленький шрифт

Самые частые размеры шрифта — `0.88rem`(≈14px, 26 использований), `0.95rem`(≈15px), `0.9rem`(≈14.4px), `0.85rem`/`0.8rem`/`0.78rem`(≈12.8–13.6px). **Значительная доля второстепенного текста на сайте — меньше 15px**, при том что аудитория (люди старшего возраста, попавшие под арест счёта) особенно чувствительна к мелкому шрифту.

## 7. Где слишком длинные строки

Не измерялось построчно (нужен визуальный проход по конкретным страницам) — заложено в план типографики (Этап 14.3: ограничение 70-75 символов в строке для юридического текста).

## 8. Где кнопки выглядят как обычный текст

Не выявлено явных случаев (все `.btn-*` классы дают явный визуальный стиль кнопки). Риск скорее обратный — слишком много визуально РАЗНЫХ кнопок (см. п.2).

## 9. Где CTA конкурируют между собой

Каталог «Реестры» в главном меню содержит **14 пунктов** в одном выпадающем списке (банки/суды/коллекторы/ломбарды/МФО и т.д.) без визуальной группировки, кроме разделителей — перегружает навигацию.

## 10. Где мобильная версия неудобна

Найдено **13 разных breakpoint-значений** (`1280, 1180, 1100, 1024, 992, 980, 900, 768, 680, 640, 600, 576, 480px`) без единой сетки — компоненты из разных CSS-файлов «переключаются» на мобильный вид в разных точках, из-за чего layout может «прыгать» несинхронно между блоками одной страницы.

## 11. Где элементы перекрываются

Не выявлено конкретных случаев в статическом анализе — требует визуальной проверки (скриншоты, Этап 14.20).

## 12. Где есть горизонтальный скролл

Не проверялось напрямую (нужен браузерный тест) — учтено в плане мобильной проверки.

## 13. Где слишком много визуального шума

Главный логотип (`zakonexpert-logo-kazakhstan.png`, **1.28MB**, не WebP) грузится в шапке И в подвале **на каждой странице** — 2.5MB+ только на логотип за один визит без даже намёка на сжатие.

## 14. Где дизайн снижает доверие

Форма проверки ИИН на главной — **самая важная конверсионная форма сайта** — использует только `placeholder`, без `<label>`. Это (а) реальная проблема доступности (placeholder исчезает при вводе, скринридеры видят поле хуже), (б) для юридического сервиса, работающего с чувствительными персональными данными, отсутствие явного label выглядит менее профессионально, чем могло бы.

## 15. Приоритет исправлений

## Не найдено проблем (проверено, чисто)

- Множественных `<h1>` не найдено в выборке — уже исправлено в прошлых этапах.
- `<div onclick>`-антипаттерн найден только в `public/rezultaty.html` (11 случаев) — больше нигде.
- Иконки-кнопки в общей шапке/подвале (`.nav-toggle`, `.sticky-wa`) уже имеют `aria-label`.
- Мобильное меню использует JS-переключение классов (`data-nav-toggle`), не чистый CSS-хак — нормальная, поддерживаемая реализация.

Дальнейшие шаги (Этап 14.2+) — строить дизайн-систему на основе этого аудита, не переписывать CSS хаотично.
